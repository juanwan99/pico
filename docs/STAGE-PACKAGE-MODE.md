# Pico 工作模式 · 阶段包（BINDING）

```
DOC: docs/STAGE-PACKAGE-MODE.md
STATUS: BINDING — 业主 2026-08-02 对齐 edu-core 阶段包
SUPERSEDES: 默认多窗碎卡调度；日常「执行完毕审查」微观循环
KEEPS: 真源纪律、红线、不自 PASS、Kimi 受控、#170 须授权
SEE: docs/AUTONOMOUS-GOAL.md（总目标 A–I 仍为成功定义）
      docs/FAST-PATH.md（技术节奏可参考，服从本页组织法）
REPO: juanwan99/pico ONLY
PROD: https://pico.aivia.asia
```

## 1. 一句话

```text
阶段总计划 → 单窗 Agent 自治执行 → 一份阶段成果包 → 业主验收
总管写计划与禁区、阶段末核真源；不靠多窗碎卡磨洋工。
```

## 2. 角色

| 角色 | 做什么 | 不做什么 |
|------|--------|----------|
| **业主** | 定方向/阶段目标；**只审阶段成果包**（ACCEPT / REVISE） | 不盯每个 PR；不跑命令；不代工程细节 |
| **总管** | 写阶段总计划（DoD/禁区/红线）；阶段末对照 tip/部署/SMOKE 核真源；出 SOLO 卡 | 不日常碎催；不默认三窗微观调度 |
| **执行窗（默认 1 个）** | 按总卡端到端：代码→CI→合→部署→SMOKE→成果包 | 不等人派十张小卡；不并行抢同一仓 |
| **独立审查（可选）** | 阶段末只读深审 | 不代签产品；默认不改码 |

**窗口编号（Pico 映射）：**  
历史「窗1部署 / 窗2写码 / 窗4验证」**合并为执行窗 SOLO 职责**（同一 agent 可串行完成）。  
不再默认同时派 1+2+4 三张卡。

## 3. 为什么对齐

| 旧 Pico 问题 | 阶段包对策 |
|--------------|------------|
| 修→装→验多卡循环 | **一张阶段总卡** |
| 多窗分派、总管高频审 | **单窗**端到端 |
| 业主被「执行完毕审查」拖住 | **只审成果包** |
| 有推进但完成感差 | **DoD 写死再开干** |

## 4. 标准流程

```text
1. 总管出「阶段总计划」
   - 一句话目标
   - DoD（可勾选，对齐 AUTONOMOUS-GOAL A–I + 本阶段残留）
   - 范围 / 禁区 / 红线
   - 成果包格式
   - 业主验收点（≤6 条）
2. 总管出「标准任务卡」×1（单窗 · CLEAR）
   - 贴阶段 Issue；其它并行写码窗停止
3. 执行窗 CLAIM → 内部自排 → 少 PR 多成色
   - 绿/黄：CI 绿可合
   - 阶段内部署：建议 **1～2 次**（功能齐再装，或中期一次+收口一次）
4. 功能齐 → 部署（exact tip）→ 全量 SMOKE（登录/聊/停/重跑/产物/S7/无 FNF）
5. 阶段 Issue 交「阶段成果包」
6. 业主 ACCEPT | REVISE
   - 工程 SMOKE ≠ 产品 PASS
   - 需要时再加独立只读审查
```

## 5. 任务卡最小结构（SOLO）

```text
【Pico 阶段 SOLO 卡】
执行窗：SOLO（唯一）
上下文：CLEAR | KEEP
阶段名 / RISK
BASE tip + 线上 tip（执行前 gh 校准）
一句话目标
内部建议顺序（可选，不拆成多 Issue）
DoD 清单（可勾选）
禁区 + 红线
成果包要求
CLAIM 句式
```

**不再默认：** 每能力一张碎卡、独立部署卡、独立验证卡、每步总管审查。

## 6. 真源纪律（不变）

| 真源 | 用途 |
|------|------|
| GitHub `main` SHA | 代码 |
| 部署 tip / health.git_sha | 线上 |
| 阶段 Issue | CLAIM、部署回执、成果包 |
| `docs/AUTONOMOUS-GOAL.md` A–I | 成功门禁定义 |
| 公网 health / 登录 | 活着 |

口头完成不算；**部署成功 ≠ 产品验收**；**CI 绿 ≠ product PASS**。

## 7. 质量闸（轻量但硬）

- **红线：** 唯一写仓 pico；禁 edu-cloud 写；禁 PROXY=1；禁密钥进仓；禁 Plan B 换核；禁假「Kimi 接入完成」；工具 AllowlistGateway；危险工具默认关；**#170 默认切流须业主书面**；canary 不擅自扩
- **阶段末：** 总管对照 DoD 核 tip/部署/SMOKE（可加独立审）
- **业主：** 按成果包演示步骤手测后 ACCEPT/REVISE
- **诚实：** 成果包必须写「未做」

## 8. 阶段成果包格式（执行窗必交）

```text
## 阶段成果包
- 阶段名:
- tip (main):
- production git_sha:（必须一致才可请签）
- PR 列表:
- DoD 勾选表:（逐条 PASS/FAIL + 一句话证据）
- SMOKE 步骤与结果:
- 未做 / 残留风险:（≤5）
- product PASS: NOT CLAIMED
- orchestration complete: NOT CLAIMED
- 请业主：ACCEPT | REVISE（注明条目）
```

Issue 标题前缀：**`STAGE:`**（进行中）→ 成果包就绪后改或另开 **`OWNER-ACCEPT:`**。

## 9. 适用 / 不适用

| 适用 | 不适用 |
|------|--------|
| 有清晰 DoD 的竖切阶段 | 无目标的「先做着」 |
| 单仓 Pico 主链 | 未授权的 #170 / 换核 |
| 要速度的日用可靠 | 极高危全库重构（可 SOLO 但 DoD/审更严） |

## 10. 业主开新阶段口令

```text
按阶段包模式：目标=……；禁区=……；执行单窗。
总管出总计划+一张 SOLO 卡。
```

总管只回：**阶段总计划 + 一张 SOLO 卡**。

---

**一句话：单窗、大阶段、死 DoD、一份成果包、业主终审；总管管方向与真源，不管碎步。**
